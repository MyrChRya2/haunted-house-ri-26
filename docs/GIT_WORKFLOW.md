> 对象：Ray 与 Illya。**Illya 是 git 新手——本文件只要求照做，不需要理解原理。**
> 四条铁律：`main` 永远可运行 · **小步提交** · **不 force push** · 提交前先 pull

> ⚠️ **2026-10-06 按 Ray 的裁决调整：分支制取消，Illya 可以直接推送到 main。**
> 原规则（2026-09-23 Ray 定）："以后正在开发的功能或者内容先不要推送到 main 上面，而是单独开一个分支，完成正在开发的部分再合并到 main 里"。
> Illya 于 10-06 提出"我开发的内容也可以直接推送到 main"，**Ray 已同意**。现在：
> - **开发内容可以直接提交并推送到 main**，不必先开分支、不必等合并；
> - **分支变成可选**（只在想做实验、或改动很大想留退路时用）；`Merge PR` 仍由 Ray 或项目管理 Agent 操作；
> - **唯一硬要求：main 必须保持"能打开、能跑"** —— 推送前自测一次；确知会暂时推坏就在群里说一声（谁后推谁负责尽快修回）。

## 一、什么走分支、什么可以直接进 main

| 改动类型 | 走哪 | 说明 |
|---------|------|------|
| 游戏功能、场景、脚本、素材 | **可以直接进 main** | 2026-10-06 Ray 裁决；推送前确认工程能打开 |
| 工程配置（`project.godot`、导出预设、autoload） | **可以直接进 main**，但**改完必须当场验证工程能开** | 工程配置错了会让全队打不开，是风险最高的一类 |
| 项目管理文档（`docs/`、`PROJECT_INDEX.md`） | main（由 Agent 提交） | 文档是记录，天天要走分支会拖垮协作节奏 |
| 想做实验 / 大改动想留退路 | **分支（可选）** | 分支不再是强制，只是工具 |

> 判断口径不再是"要不要开分支"，而是：**"这次推送会让 main 跑不起来吗？"** 会 → 要么别推，要么先说一声。

## 二、开工前一次性准备

1. 装 **Godot 4.7.1**，版本与 Ray **完全一致**（版本不一致会出现"场景打不开"）。
2. 装 **GitHub Desktop**，登录你自己的 GitHub 账号。
3. 接受 Ray 发来的 collaborator 邀请（私有仓库只有被邀请的人能看）。
4. GitHub Desktop → `File → Clone repository` → 选本项目的仓库 → 选一个本地目录。
5. 提示：**不要**用 `New repository`，仓库已经存在，用 `Clone`。

## 三、一轮开发的完整流程（六步）

### 第 1 步 · 先同步 main

GitHub Desktop 顶部 `Current Branch` → 切到 **main** → 右上 `Fetch origin` → 有更新就 `Pull origin`。
**永远从最新的 main 切分支出来**，否则一开工就是冲突。

### 第 2 步 · 开一个新分支

`Current Branch` → `New Branch` → 起名（见第四节命名规则）→ `Create Branch`。
此刻你的改动就和 main 隔离了。

### 第 3 步 · 开发 + 小步提交

在 Godot 里改你的场景 / 脚本，按 F5 能跑通就提交一次：
左侧勾选改动 → 左下写一句话 → `Commit to <你的分支名>`（**注意不是 main**）。

### 第 4 步 · 推送你的分支

右上角 `Push origin`（第一次会显示 `Publish branch`）。
**不 push 等于没做** —— Ray 那边看不到你的进度。

### 第 5 步 · 发 Pull Request（请求合并）

1. 打开 https://github.com/MyrChRya2/retro-game-jam-2026 ，页面顶部会出现 **Compare & pull request**，点它。
2. 标题写清楚（例：`feat: 第一关场景与碰撞`），描述里写"做了什么 / 怎么验证的"。
3. 点 `Create pull request`。**不要自己点合并** —— 由 Ray 或项目管理 Agent 合并。

### 第 6 步 · 合并之后

合并完成后：切回 `main` → `Fetch/Pull` 拿到合并结果 → 删掉本地那个分支（`Branch → Delete`）。
下一轮再从第 1 步开始。

## 四、分支怎么命名

`类型/谁-做什么`，全小写、用连字符：

- `feat/illya-level-01` —— Illya 做第一关
- `feat/ray-sprites` —— Ray 做精灵图
- `fix/illya-wall-collision` —— 修贴墙 bug

一条分支**只做一件事**；**不设时间限制，确定完成了再合并到 main**（不急、不赶，但别在没做完的状态下合并）。

⚠️ 分支存活期间 main 会继续前进，两边差距越大，最后合并越痛。所以请**定期**用
`Branch → Update from main` 把 main 合进你的分支（建议每完成一小块就做一次，见第八节第 4 条）。

## 五、提交信息怎么写

格式：`类型: 简短描述`（前缀英文小写，描述中英文都行）

| 前缀 | 什么时候用 | 例子 |
|------|-----------|------|
| `feat` | 新增功能 | `feat: 玩家移动与碰撞` |
| `fix` | 修 bug | `fix: 贴墙时角色卡住` |
| `art` | 美术资源（Ray） | `art: 复古 tile 集` |
| `audio` | 音频资源（Ray） | `audio: 跳跃音效` |
| `docs` | 文档 | `docs: 更新 GDD 核心循环` |
| `chore` | 杂项配置 | `chore: 调整重力参数` |

**别写** `update`、`改了一下`、`.` 这类信息 —— 一周后没人知道那次改了什么。

## 六、什么时候该提交

1. **一个能跑通的状态 = 一次提交**（按 F5 能正常运行再提交）。
2. **别攒超过半天** —— 攒得越久，冲突越大、越难修。
3. **每天至少 push 一次**，哪怕只做了一点。

---

## 七、绝对不要做的事

1. **不要把 main 推成"打不开 / 跑不起来"的状态** —— 2026-10-06 起允许直接推 main，但推送前请自己打开工程确认一次；确知会短暂推坏就先在群里说一句。
2. **不要 force push**（GitHub Desktop 中名为 `Force push`）—— 会覆盖别人的提交。真有需要，先在群里问。
3. **不要自己合并 PR** —— 合并前要确认工程能打开、能 F5，这一步交给 Ray 或项目管理 Agent。
4. **不要改 `project.godot`、`export_presets.cfg`** —— 工程配置归 Ray 独占，改错会让整个工程打不开。
5. **不要提交 `.godot/` 目录** —— 导入缓存，`.gitignore` 已自动忽略，别手动强加。
6. **不要提交导出产物**（`.wasm`、`.pck`、`.zip`、`EXPORTS/`）—— 库里已经有规则挡着。
7. **不要改别人负责的场景** —— 一人一场景，谁建谁改。
8. **不要手删或手改 `.uid` 文件** —— Godot 4.7 用它做 UID 映射，删了主场景会找不到。
9. **不要提交大于 10MB 的文件**（音频、图片先问 Ray 统一处理）。

## 八、冲突了怎么办

1. **现象**：`Pull` 时提示冲突，或 GitHub Desktop 让你选保留哪一边。
2. **动作**：**立刻停下**，在群里说一声，把截图发出来，让 Ray 或项目管理 Agent 处理。
3. **尤其 `.tscn` 场景文件冲突** —— 不要自己选"保留我的/保留对方的"，那会静默丢掉一半内容。
4. **让分支跟上 main**：如果开发期间 main 有更新，用 `Branch → Update from main` 把 main 合进你的分支 —— 别拖着到最后一起撞。
5. **预案**：谁后 push 谁负责解决；场景冲突找建该场景的人拍板；实在乱了就回到最近的 tag 重来。
