## 决策与理由

- **采用「抽 TileSet 为独立 `.tres` + 中立 map 模板」**，理由：
  1. `TileSet` 本身就是 `Resource`，**设计上就可被多个 `TileMapLayer` 共享**；内嵌只是编辑器默认行为，不是限制。
  2. 抽成 `.tres` 后，新建关卡只需 `添加节点 → TileMapLayer` → 加载该 `.tres` —— **物理碰撞、图集、terrain 一次到位，不需重画**。
  3. 改一次图集（补格子、调多边形）**全关卡生效**，不必逐关同步。
  4. **今天做不亏**：双网格（GDD 3.4 D5，刚需）落地后大概率是「两个 `TileMapLayer` 共用同一 `TileSet`」，正好就是共享 `.tres` 的形态；但**不为此提前改动图集排布**，等 Illya 交出三个参数。
- **地图数据仍走「覆盖 `tile_map_data`」**，不强上继承场景：`tile_map_data` 是 `TileMapLayer` 的普通属性（`PackedByteArray`），父子场景各自覆盖即可，机制简单、level3 已验证可行。
- **模板要中立**：不叫 `level2/map.tscn`，另立 `scenes/levels/map_template.tscn`。现有 level3 直接挂在 level2 的文件上，是**耦合**，不是继承。

## 追加：把 level2 的地图当 level3 的「参考底图」怎么做

Ray 问：画 level3 时能不能把 level2 的地图拖进 level3 的节点树当参考。**能，但拖进来的是"活的实例"而不是"参考图"。**

**现状核对**：`level3.tscn` 里已经有一个 `Map` 节点是 `level2/map.tscn` 的实例（覆盖了 `tile_map_data`）。**再拖一份进来 = 同一关卡里两个 level2 地图实例。**

**三个必做动作**：

| # | 设置 | 为什么 |
|---|------|--------|
| 1 | **关掉参考层的 `Collision Enabled`** | `TileMapLayer` 默认 `collision_enabled = true`，而该 `TileSet` 的 `physics_layer_0/collision_layer = 1` —— 两层墙都在碰撞层 1，**参考层会和真地图一起挡玩家**，表现是"没画墙却撞住"的**空气墙** |
| 2 | `Modulate` 的 alpha 调 0.3~0.5 + `Z Index = -1` | 半透明压在下层才看得清自己的笔迹 |
| 3 | 命名 `REF_` 前缀；**不要在这个实例上画画** | 在实例上落笔＝给 level3 的 `tile_map_data` 写覆盖 → ① 它**不再跟随 level2**（覆盖顶掉实例数据）② 分不清哪格是参考、哪格是自己画的 |

> ✅ **已核对 Godot 4.7.1 引擎 API**（`--dump-extension-api` 导出 `extension_api.json` 后解析）：`TileMapLayer` 的完整属性为 `tile_map_data / enabled / tile_set / occlusion_enabled / y_sort_origin / x_draw_order_reversed / rendering_quadrant_size / collision_enabled / use_kinematic_bodies / collision_visibility_mode / physics_quadrant_size / navigation_enabled / navigation_visibility_mode`。**`enabled`**＝整层关掉（不渲染也不碰撞），**`collision_enabled`**＝只关碰撞。两个属性名都确认存在，不是凭印象说的。

**换个角度：如果 level3 是箱庭拼图（level2 的房间 + 新区域接起来），可能根本不需要两层** —— 直接在现成的 `Map` 实例上改，level2 的数据本身就是你的起稿底图。判据：
- 「只要看着 level2 的墙在哪，好对齐我的新墙」→ 加参考层（关碰撞 + 半透明）
- 「level3 就是从 level2 长出来的」→ 别加层，直接改现成那个

**最稳的替代**：把「level2 参考实例 + 你的新层」放进 `dev/` 下的临时场景（按项目约定 `dev/` 不进 main），这样参考层**绝不可能混进正式关卡**。或者干脆截一张 level2 的图当参考图。

## 追加 2：瓦片遮挡（上半遮挡 / 下半不遮挡）

Ray 反映：「带视差的瓦片，实际物理碰撞层与瓦片贴图并不完全重叠，导致玩家精灵渲染在墙上」—— 问能否让某些瓦片**上半部分遮挡、下半部分不遮挡**。

**先立结论**：Godot 的遮挡粒度是**整个瓦片（一格）** —— `TileData` 的 `z_index` / `y_sort_origin` 都作用于**整格**，**不存在"同一个瓦片只遮上半"**。要半格级遮挡，只能把墙**拆成上下两个瓦片**，分别放到玩家**后面**和**前面**。

**✅ 已核对 Godot 4.7.1 引擎 API**（`--dump-extension-api`）：

| 属性 | 所属类 | 粒度 | 作用 |
|------|--------|------|------|
| `y_sort_enabled` | **`CanvasItem`** | 节点 | 开启 Y 排序（`TileMapLayer` / `Node2D` / `Sprite2D` 都继承） |
| `z_index` / `z_as_relative` | **`CanvasItem`** | 节点 | 整层前后关系 |
| `z_index` | **`TileData`** | **逐瓦片** | 该瓦片的前后偏移（整格） |
| `y_sort_origin` | **`TileData`** | **逐瓦片** | 该瓦片的 Y 排序原点（整格） |
| `texture_origin` | **`TileData`** | **逐瓦片** | 贴图相对格子的偏移 —— 视差 / 贴图与碰撞错位就靠它 |
| `y_sort_origin` | `TileMapLayer` | 整层 | 整层的排序原点 |

**⚠️ 需求澄清（Ray 后续补充）**：他要的不是"固定只遮上半格"，而是**「玩家站墙后被墙遮、站墙前遮住墙」的自动翻转** —— 这正是 Godot 原生的 **Y 排序（Y-sort）**，**不需要拆瓦片、不需要改美术**。（本段原先把"拆两层"并列为首选，属误判，已更正。）

**四条开关，少一个就不生效**：

| # | 动作 | 为什么 |
|---|------|--------|
| 1 | **墙单独一层** `TileMapLayer`（如 `Walls`），地面留 `Ground` 层并设 `z_index = -1` | `TileMapLayer.y_sort_origin` 是**整层**偏移；墙与地板混在一层，一加偏移地板也跟着偏 |
| 2 | **共同父节点（关卡根）与 `Walls` 层都开 `Y Sort Enabled`** | 该属性来自 `CanvasItem`，语义是"给**它的子节点**排序"；两者必须是**同一父节点的兄弟**才会互相比大小。玩家节点本身**不用**开 |
| 3 | 给墙瓦片设 **`TileData.y_sort_origin`**（TileSet 编辑器里选中瓦片） | 排序值 = 全局 y + `y_sort_origin`。**默认 0＝按格子顶边比** → 玩家永远被墙压住。要的是**墙脚那条线**：16px 瓦片设 **16**（＝格子底边）。视差贴图上移了，可微调到 8~12，原则是**把原点落在"希望前后翻转"的那条线上** |
| 4 | **玩家节点原点放在脚底** | 排序用的是**节点自身的原点**，不是精灵中心。原点在身体中间 → 差半格，表现是"人已绕到墙后却还在墙前"。做法：`Sprite2D` 的 `Offset.y = -8`（16px 精灵）上移。**门 / 道具 / 怪物同理** |

**验证**：在编辑器里拖玩家的 y，看前后关系是否在"脚底跨过墙脚线"那一刻翻转；翻转点偏了就调 `TileData.y_sort_origin`。

**不生效的常见原因（按概率）**：① 父节点没开 `y_sort_enabled`（只开了 TileMapLayer）→ 各排各的 ② 玩家原点不在脚底 ③ 墙与玩家不在同一父节点下 ④ 墙瓦片 `Y Sort Origin` 还是 0 ⑤ 某层设了 `z_index` 把整层抬走 —— **`z_index` 优先于 Y 排序**，所以 `Ground` 设 `-1` 是对的，但别给 `Walls` 设 `z_index`。

**另一条路（仅当真要"固定只遮上半格"时才用）**：把墙拆成"上半 / 下半"两个瓦片，分放 `Walls_Back`（玩家后）与 `Walls_Front`（`z_index` 更高）。逐瓦片 `z_index` 则**慎用** —— 它是绝对的，会把人从墙下走过时也压住，只适合门框 / 天花 / 前景装饰。前景区**不必改图集**：新建 `TileMapLayer` 把 `tile_set` 指向**同一个 `.tres`**（呼应「追加 1」）即可。

**先在 `dev/` 里试，别在 6 关正式场景上直接改。**

## 追加 3：地板不可见时的简化（Ray 补充：墙瓦片连地板一起、地板与背景都是纯黑）

**前提修正**：地板与背景同为纯黑、且**只有墙有碰撞**，所以「地板」这一层在视觉上**可以完全忽略**。由此：

- ✅ **不需要为 Y 排序去拆"地板层 / 墙层"** —— 我先前那条"必须拆层"的顾虑（整层 `y_sort_origin` 把地板一起带偏）在**地板不可见**的前提下**不成立**：黑块偏不偏都一样。
- ⚠️ **但有一条硬规则**：**参与 Y 排序的层里只能放"需要遮挡玩家"的东西**（墙身）。**纯黑瓦片绝不能进这一层** —— 它们一旦被 Y 排序盖到玩家身上，表现是**玩家凭空消失**（黑盖黑）。纯黑地板要么不画，要么放下面一层（`z_index = -1`、**不开** Y 排序）。
- 极端简化：**地板既然不可见就直接不画** → 只剩墙瓦片一层、一个统一的 `y_sort_origin`，最省事。

**⚠️ 必须验证一件事：墙瓦片格子里那块"能走的地方"，在贴图里是透明还是黑色？**
（`map.tscn` 的 `physics_layer_0` 多边形是**带缺口**的，说明墙格内确有可行走区域。）

- 贴图里是**透明**（只是看着黑，因为背景黑）→ 直接可用，没有任何副作用。
- 贴图里是**黑色** → Y 排序后那块黑会**盖住**站进去的玩家 → 必须把"可行走的黑地板"从墙瓦片里**拆出来**单独做瓦片，放到下层。

**测试**：站进墙格的可走区域，看角色是否被黑块吞掉。

**操作清单（最终版）**：① 现有那层改名 `Walls`，开 `Y Sort Enabled`，**`z_index` 保持 0 不要设**；② 关卡根节点也开 `Y Sort Enabled`；③ 若有纯黑地板层 → 放前面 + `z_index = -1` + **不开** Y 排序；④ TileSet 里选墙瓦片设 **`Y Sort Origin`**（先试 16＝格底，再按"墙脚那条线"微调，视差贴图别死记 16）；⑤ 玩家 `Sprite2D` 的 `Offset.y = -8` 让原点落到**脚底**；⑥ 门 / 道具 / 怪物同理。

**另注**：Y 排序只解决**绘制顺序**，不解决碰撞形状 —— 如果玩家还能站进墙里，那是碰撞多边形该不该留缺口的问题，两件事分开处理。

## 追加 4：terrain 规则 / 碰撞 / Y 排序是三件互不干扰的事（Ray 补充）

Ray 补充：**瓦片的地形（terrain）规则是按纯黑地板画的**，**物理碰撞是按墙面画的**，**地板与墙面在同一个 TileSet 资源里**。

**结论：这不冲突，也不影响方案。** 三者各管各的：

| 机制 | 管什么 | Y 排序会不会破坏它 |
|------|--------|------------------|
| `terrains_peering_bit`（terrain 规则） | **选哪个变体**（自动接边） | **不会** —— 排序只在绘制阶段生效 |
| `physics_layer_0`（碰撞多边形） | **哪里能走** | **不会** |
| `TileData.y_sort_origin` | **谁画在谁上面** | 只加了一个排序键 |

**同一 TileSet 里地板与墙面在一起也没问题** —— `y_sort_origin` 是**逐瓦片**属性，不同瓦片可以给不同值。

**🔑 取值原则**：`y_sort_origin` ＝ **该瓦片的"墙脚线"距格子顶边的像素数**（＝你希望玩家"从这条线以下走过来就能盖住墙"的那条线）。**不是 0，也不一定是 16。**

从 `level2/map.tscn` 的碰撞多边形实测（格子 16×16，坐标 -8..8，换算 px = y+8）：

| 瓦片 | 碰撞多边形底边 | 墙脚线 |
|------|---------------|--------|
| `0:0` / `5:0` | 局部 y=1 | **≈ 9 px**（半高墙，这是多数） |
| `0:1` | y=8 | 16 px（整格高） |
| `1:1` | **没有多边形** | 纯地板瓦片（无碰撞） |

→ 所以**不能整层设一个值**，要逐瓦片设。TileSet 编辑器中可**框选多个瓦片批量设**。

**⚠️ 必须处理的一条**：**纯地板瓦片（如 `1:1`，无碰撞）如果留在开了 Y 排序的层里，会跟着排序、可能盖住玩家**（黑盖黑＝玩家消失）。按难度递增三选一：
1. **不铺/删掉**——地板和背景同色看不见，但 ⚠️ terrain 自动接边可能依赖地板连通性，删前先在 `dev/` 验证；
2. **给地板瓦片设负的 `Y Sort Origin`**（如 `-16`）让它永远排在玩家之下 —— 一层搞定、不用重画，⚠️ 恰好在整数格边界上可能并列，要实测；
3. **拆两层**：`Ground`（纯地板瓦片、**不开** Y 排序、`z_index = -1`）+ `Walls`（开 Y 排序）—— 最稳，但要处理重画。

**落地建议（时间紧）**：**别一次调 48 个格** —— 先挑玩家真会绕过去的那 2~3 面墙的瓦片调对，其余保持默认；全部在 `dev/` 里验证完再落到正式关卡。

### ⚠️ 副作用：`Cover` 压到了玩家那块黑色遮罩之上

**现象（2026-10-07）**：玩家为实现"点火照亮"叠加了一块很大的黑色遮罩（在 `Player/MatchLight/VisionMask`，`ColorRect` + `vision_mask` 着色器，属 **Illya 负责**），`Cover` 抬到 z=1 之后，**墙面被渲染到遮罩之上** → 黑暗区域里也能看见墙，照亮效果被破坏。

**原因**：`VisionMask` 没有自己的 `z_index` → 有效 z ＝ **0**（与玩家同层，原本靠"在 `Player` 之下、树顺序靠后"压住玩家）。而 `Cover` 是 **1** → **z 更大者在上** → `Cover` 盖过遮罩。
**⇒ 只靠树顺序排出来的层，会被任何新加的 `z_index` 打乱。**

**修法：把遮罩的 `z_index` 提到 `Cover` 之上。** 遮罩本来就是"整屏黑暗 + 玩家周围一个洞"，**语义上就该是世界里最上面的一层**：

| 层 | 有效 z |
|---|---|
| `CanvasLayer`（HUD，独立 canvas） | 永远最上 |
| **`VisionMask`** | **5** ← 黑暗遮罩（世界最上） |
| `Darkedge` | 2 |
| `Cover` | 1 |
| `Player` | 0 |
| `Background` | -1 |

**两条注意**：① **这是 Illya 的系统，改前先跟他说一声**（已沟通：**Illya 授权 Ray 全权修改**）；② 提上去之后注意**玩家在光洞里是否被压暗**。

### 🔴 更正：遮罩**必须留在玩家之下** —— 靠 `z_index = 5` 是错的

**实测证据（`match_light.gd` + `vision_mask.gdshader`）**：
- `VisionMask` 是 2048×2048 的 `ColorRect`，着色器输出 **黑色 + alpha = 1 − mask_tex.r**；
- **`radius = 0` 时 `a = 1.0` → 整块纯黑、完全没有洞**（`extinguish()` 里就是 `_set_radius(0.0)`，那是**未点火**的常态）；
- `match_light.gd` 第 40 行 **`show_behind_parent = true`** 是**刻意**的：让遮罩画在 `Player` 之下 —— **这样全黑时玩家仍然看得见**。

⇒ 把 `VisionMask.z_index` 提到 5，**z 的优先级高于 `show_behind_parent`**，遮罩跑到玩家之上 → **未点火时玩家被整块黑盖住**（Ray 实测确认）。

**而遮罩又必须在 `Cover` 之上**（否则黑暗区里的墙会透出来，破坏氛围）。
⇒ 需求是 **`Cover` ＜ `VisionMask` ＜ `Player`** —— 而 `Cover`=1、`Player`=0，**整数 z 之间塞不进值**，所以必须**把玩家抬上去**，并让遮罩用**绝对 z**。

### ✅ 最终 z 序（数值留大间隔，便于以后插层）

| 节点 | 所在场景 | `z_index` | `Z as Relative` |
|------|---------|-----------|-----------------|
| `Background` | `levelN.tscn` → `Wall` 下 | **-10** | 默认开 |
| `Cover` | `levelN.tscn` → `Wall` 下 | **10** | 默认开 |
| **`VisionMask`** | `Player.tscn` → `MatchLight` 下 | **20** | ⚠️ **必须关掉** |
| **`Player`** | `container.tscn`（实例覆盖） | **30** | 默认开 |
| `Darkedge` | `levelN.tscn` → `Wall` 下 | **40** | 默认开 |
| `CanvasLayer`（HUD） | `Player.tscn` | — | 独立 canvas，永远最上 |

⚠️ **`VisionMask` 的 `Z as Relative` 必须关掉** —— 否则有效 z ＝ `Player(30) + 20 = 50`，又跑到玩家上面去了。

⚠️ **副作用（须知情）**：把 `Player` 抬到 30 之后，**关卡里 z=0 的东西（门 / 道具 / 怪物）都会排在玩家之下**。通常没问题（玩家在最前），但若发现某样东西应该盖住玩家，就给它单独设一个 >30 的 z。

📌 `Background` / `Cover` / `Darkedge` 的 z **每关各一份**（都在 `levelN.tscn` 里），所以 level2~10 也要照做；`Player` 与 `VisionMask` 各只有一处（`container.tscn` / `Player.tscn`）。

### ✅ 结论：`vision_mask.gdshader` **不需要重做** —— 它已经就是 Ray 要的逻辑

**Ray 的设想（原话）**：「除了玩家精灵图，其余像素全部渲染为黑色。当按下点火键时，逐帧播放遮罩序列帧，被遮罩里白色区域覆盖的话就正常渲染颜色，被遮罩黑色区域覆盖的话就保持只渲染为黑色。」

| Ray 的描述 | 着色器现状（逐行核对） |
|---|---|
| 其余像素全黑 | `COLOR = vec4(0,0,0,a)`，未点火时 `radius = 0` → `a = 1.0` → **整屏纯黑** ✓ |
| 白色区域正常渲染 | `a = 1.0 - texture(mask_tex, uv).r` → 白 `r=1` → **a=0 透明** → 底层画面透出 ✓ |
| 黑色区域保持黑 | 黑 `r=0` → **a=1 不透明黑** ✓ |
| 逐帧播放序列帧 | `uv.x = (uv.x + f) / n` 按 `frame` 在横排图里切格 ✓ |
| 除了玩家精灵图 | 遮罩画在 `Player` **之下**（`match_light.gd:40` 的 `show_behind_parent`）→ 玩家永不被盖 ✓ |

**⇒ 需求 = 现有着色器 + 正确的 z 序。问题从来不在着色器，而在"谁压谁"。**

**两处按该逻辑的微调**：
1. **`Darkedge` 应放在遮罩之下**（z＝**15**，而非 40）—— 严格符合"除了玩家其余全黑"。差别很小（Darkedge 本身是暗的、光洞里照样可见），但按原话应置于遮罩下。
2. **`IgniteFlash`（火花）需盯一眼** —— `match_light.gd:47` 注释写明「火花画在遮罩上面：黑底上亮一下，墙不挡它」，是**刻意**的。它现为相对 z（跟随 `Player`）；玩家抬到 30 后若发现火花被遮罩吃掉，给它单独设 **`z_index = 25`**（遮罩 20 之上、玩家 30 之下）。

### 🎯 最终实际配置（2026-10-07 实测文件后确定，只需改 1 个值）

**Ray 的疑问**：「遮罩应该不会被渲染才对，遮罩只是参与计算要渲染的像素，不需要被渲染。」

**⇒ 这个前提不成立**：`VisionMask` 是 `ColorRect`，着色器输出的是 `COLOR = vec4(0,0,0,a)` —— **它就是一块"带洞的黑色方块"，是实打实被画出来的**。Godot 2D 里"把像素变黑"只有靠画东西这一条路（想要"只参与计算"得换 `CanvasModulate` + `Light2D` 那套光照系统，是另一条技术路线，**冻线前绝不动**）。既然它在画，就必然有前后顺序 —— **只能排，没法绕。**

**实测现状（问题所在）**：

### 转向「只参与计算」的路线（Ray 决定，时间自评够用）

**思路**：不再画黑方块，而是用 Godot 原生 2D 光照 —— 整个画布调暗，只有光源半径内显色。

| 步骤 | 做法 |
|------|------|
| ① 加 `CanvasModulate` | 放在 **`container.tscn` 的 `Container` 下**（每个 canvas 只有**最后一个**生效，放一处最好），颜色设深色（如 `Color(0.05,0.05,0.08)`） |

### ✅ 更正（我上一条的"光照做不到"判断是**错的**）：Godot 2D 光照是「乘法」的，方案可行

**正确的模型**：光照管线先算出**光照总量** ＝ `CanvasModulate`（环境光）＋ Σ(各 `Light2D` 的贡献)，再把物品颜色**乘以**这个总量。
`Light2D.BlendMode`（`ADD`(0) / `SUB`(1) / `MIX`(2)）描述的是**光怎么并入「光照总量」**，不是直接往屏幕上加。

| 配置 | 光照总量 | 结果 |
|------|---------|------|
| `CanvasModulate = 黑`，无光 | 0 | 颜色 × 0 ＝ **纯黑** ✓ |
| `CanvasModulate = 黑`，白光 `energy = 1` | 0 ＋ 1 ＝ **1** | 颜色 × 1 ＝ **还原原色** ✓ |

**⇒ 「暗处纯黑 + 亮处原色」用光照**完全可以做到**，「遮罩」并非唯一解。** 上一条的结论作废。

**复用现有 `Player/MatchLight/Light` 需要改的地方**：① 删掉脚本 `_ready()` / `extinguish()` 里的关灯与 `energy = 0`；② `Light.texture` 换成**径向渐变白光图**（不必另画 —— 新建 `GradientTexture2D`：`Fill = Radial`、`Fill From (0.5,0.5)`、`Fill To (1,0.5)`、渐变白→黑）；③ 半径用 `texture_scale`，`height` 保持 0；④ `shadow_enabled` 保持关（本项目没做 Occluder）；`range_item_cull_mask = 3` 已覆盖光照层 1、2 不用改；⑤ ⚠️ **检查 `Range Z Min` / `Range Z Max`** —— 光照只影响 z 落在此区间的 item，`Background` 在 z=-1，若 `Range Z Min` 为 0 则地板照不亮，需设成负数（如 -1024）。
另：`CanvasModulate` 建议**先设纯黑 `(0,0,0,1)`**（正是要的效果），并给 `Player/BodySprite` 设 `Light Mode = Unshaded`（否则未点火时玩家自己也全黑）。

### ✅ 更正：`Light Mode` **不在 `CanvasItem` 上，而在 `CanvasItemMaterial` 上**

**实测（4.7.1 全量属性表）**：`CanvasItem` 的属性是
`visible / modulate / self_modulate / show_behind_parent / top_level / clip_children / light_mask / visibility_layer / z_index / z_as_relative / y_sort_enabled / texture_filter / texture_repeat / material / use_parent_material` —— **没有 `light_mode`**。

它位于 **`CanvasItemMaterial`**（属性：`blend_mode` / **`light_mode`** / `particles_animation` / ...）。
（**Godot 3 里 `light_mode` 是 `CanvasItem` 的属性，Godot 4 搬到了 `CanvasItemMaterial`** —— 我是按老版本记忆说的，错了。）

**✅ 正确做法（3 步）**：选中 `BodySprite` → Inspector 的 **`Material`** 字段 → 下拉 **`New CanvasItemMaterial`** → 点开该资源 → **`Light Mode`** 选 **`Unshaded`**。其余默认值（`Blend Mode = Mix`）正常，不影响画风。
**自查**：`Player.tscn` 里会出现一个 `[sub_resource type="CanvasItemMaterial"]` 且 `light_mode = 1`。

**⭐ 另一件事**：光源就挂在玩家身上（`Player/MatchLight/Light`），所以**点火时玩家永远在光圈中心、光照总量≈1、原色显示** —— 本来就看得见。**`Unshaded` 真正的作用是"没点火时也看得见"**，那才是必需的（否则全黑连自己都黑掉）。

### 🔧 改脚本的最小方案：**只改 `_set_radius()` 与 `_set_frame()` 两个函数**

**关键洞察**：`try_light()` / `_process()` / `extinguish()` 全都通过 `_set_radius()` 与 `_set_frame()` 间接驱动遮罩 —— **只要把这两个函数的内部实现换成"驱动灯"，所有调用点一行都不用动。**

**`_set_radius(r)` 内部改成三件事**：
1. **半径 → `texture_scale`**：`光源直径 = 贴图宽度 × texture_scale` ⇒ **`texture_scale = 半径 ÷ (贴图宽度 ÷ 2)`**（例：64×64 贴图想要 64px 光圈 → `64 ÷ 32 = 2.0`）
2. **开关灯**：`r > 0` → `enabled = true`；`r <= 0` → `enabled = false`（这样 `_ready()` 末尾的 `extinguish()` 会自动关灯，不用另写）
3. **`_current_radius` 照旧赋值** —— `is_position_illuminated()` 靠它工作，不用改

**`_set_frame(f)` 内部改成**：把 `Light.texture` 换成第 `f` 帧对应的贴图（见下）。

**另外只需删掉两处"关灯/清零"**：`_ready()` 与 `extinguish()` 里的 `_light.energy = 0.0`（留着的话，`_set_radius()` 把灯打开也没亮度）。`_light.enabled = false` 那两句可留可删，因为 `extinguish()` 会走到 `_set_radius(0.0)`。

### 📐 「照亮范围比以前大很多」的原因：两套的半径含义不同

| | 以前（遮罩 shader） | 现在（`PointLight2D`） |
|---|---|---|
| 光圈直径由什么决定 | **`radius × 2`**（`uv = local/(radius*2)+0.5`） | **贴图宽度 × `texture_scale`** |
| 取值 | `full_radius = 64` ⇒ **直径 128px / 半径 64** | 253 × 1.0 ⇒ **直径 253px / 半径 126.5** |

**⇒ 126.5 ÷ 64 ≈ 1.98，差不多正好翻倍。**
**根因**：**同一张 253×253 贴图，旧方案是"缩到 128 用"，新方案是"1:1 用"。**
**⇒ 这也和上一轮的"糊"同源** —— 从缩小 128 变成 1:1 放大近 2 倍，同样的柔边在屏幕上占的像素也多了近 2 倍。

**三条处理路**：
- **A. 调 `texture_scale`（1 秒）**：要直径 128 ⇒ `texture_scale = 128 ÷ 253 ≈ 0.506`。⚠️ **缩小会引入额外插值、更糊**；⚠️ **同时必须把 `full_radius` 改回 64**（视觉半径与判定半径要一致）。
- **B. 把 5 帧重做成 ~128px（推荐）**：`texture_scale` 保持 1.0 ⇒ **1:1 不额外糊**；`full_radius` 改 **64**；图小以后"抖动过渡"也更好画。
- **C. 保持现状**：若"点火＝照亮整屏"就是设计意图（126.5 覆盖 192×160 半对角线≈125），那现在是对的且两者一致；只需确认它不会让黑暗氛围失效。

**⚠️ 必须记住的联动**：**视觉半径**由 `texture_scale`（与帧图内容）决定，**判定半径**由 `full_radius` 决定（`is_position_illuminated()`）。**两者必须一致**，否则会出现"站在亮处却捡不到道具"。**改 `texture_scale` 时务必同步改 `full_radius`。**

### 🧩 「像素边缘模糊」的完整原因链 + 是否不可避免（Ray 追问）

**原因链（三步，缺一不可）**：
1. **`PointLight2D` 的光贴图采样过滤引擎不给开关**（godot#69613），且是**线性插值**；
2. 本项目 `Stretch Mode = canvas_items` + **9× 整数缩放** ⇒ **画面实际渲染在 1728×1440 的 framebuffer 上**，精灵/字体靠 **Nearest** 保持锐利 ✓；
3. **唯独光的贴图不受 Nearest 管辖** ⇒ 253 纹素被**放大 9 倍 + 线性插值** ⇒ 边缘成为约 **9 个屏幕像素**宽的灰阶过渡。

**⇒ 精灵是"1 纹素 ＝ 9×9 硬方块"，光边却是 9px 柔和渐变 —— 两者天然割裂。**

**✅ 诚实的结论：在「`PointLight2D` ＋ `canvas_items`」这条路上，模糊不可避免。**

**能真正拿回硬边的只有两条**：
- **① 把 `Stretch Mode` 改成 `viewport`** —— 画面（含光照）先按 **192×160** 渲染再整体 Nearest 放大 ⇒ 光照缓冲里贴图 1:1，线性过渡只有 **1 个画布像素** ⇒ 放大后是 9×9 硬块 ✓ **锐利**。
  ⚠️ **代价**：**UI 也一起变块/变糊**（GDD 3.2.1 当初选 `canvas_items` 正是为了让 UI 文字清楚）；且是**全局渲染改动**，冻线前风险高。
  💭 权衡点：**"更像老电视"其实贴合评审项 Atmosphere（是否像复古游戏）**。
  🔍 **5 分钟验证法**：临时把 `Stretch Mode` 改成 `viewport` → F5 看光边是否立刻变锐利。**若变锐利即证实上述原因链**，再决定要不要接受 UI 变糊。
- **② 回到自定义 shader**（`filter_nearest` 自己可控）⇒ 能出硬边，但 `CanvasModulate` 与遮罩**二选一**、且要重建 z 关系。**冻线前不建议。**

**冻线前的两个现实选项**：
- **接受柔边**（最省，观感像真实散射光）；
- **大颗粒抖动过渡**（推荐）：⚠️ **抖点必须够大** —— 1 纹素的抖点会被 9× 线性放大糊成灰 ✗；**做到 8~16 纹素（≈72~144 屏幕像素）的方格**，则线性插值只糊掉最外一圈、主体保留 ✓ ⇒ 观感是"像素点状光晕"，风格一致。纯美术活、半小时内、零风险。

- **A（最快）**：`match_light.gd:20` 改回 **`= 5`**。
- **B（更彻底，推荐）**：把 `_last_frame()` 改成由 **`light_frames.size()`** 决定 ⇒ **消灭"帧数有两个来源"这个隐患**，`hframes` 导出变量可废弃；⚠️ 需配合 `light_frames` 为空时的保护（否则 `light_frames[0]` 越界崩）。

**附**：`mask_fps = 12.0` ⇒ 5 帧张开耗时约 **1/3 秒**（4÷12）。想慢一点就调小（如 `8`）。`mask_sheet` 导出变量已无用但无害。

### 📐 「遮罩位置差 0.5 像素」的修法：改 `local` 的半像素补偿

**Ray 观察**：遮罩位置不对，需整体往**右下**偏移 0.5 像素。

**成因**：`ColorRect` 的 `position = -MASK_SIZE * 0.5`（＝(-1024,-1024)，整数）⇒ 遮罩中心落在**玩家的节点原点**上；而节点位置被 `snap_2d_transforms_to_pixel` 吸附到**整数**，整数坐标是**像素的左上角**，不是像素中心（中心在整数+0.5）⇒ 采样的中心点落在**像素交界**上，于是整体差半个像素。

**⚠️ 为什么不能直接改节点的 `position`**：`project.godot` 里开着 `2d/snap/snap_2d_transforms_to_pixel=true` ⇒ 给 `VisionMask.position`（或 `MatchLight.position`）加 0.5 **很可能被吸附回整数**（可试，但别指望）。

**✅ 可靠做法：在 `vision_mask.gdshader` 里给 `local` 加半像素补偿**（`local` 就是"该像素相对遮罩中心的坐标"，改动它等于平移遮罩）。

**方向对照（符号试一次就知道，反了直接反号）**：
| 想要内容移动的方向 | `local` 怎么改 |
|---|---|
| **往右下 0.5 px**（Ray 要的） | **减去** (0.5, 0.5) |
| 往左上 0.5 px | 加上 (0.5, 0.5) |
| 只往右 | 只减 x 那个分量 |

**推导（备忘）**：`local` 增大 ⇒ `uv` 增大 ⇒ 采到图中更右下的纹素 ⇒ 显示在同一像素 ⇒ **内容往左上移**；故要往右下移须**减去**。等价于"把遮罩中心当作位于其左上 0.5 处"。

**替代**：若吸附未发生，直接给 `VisionMask.position` 加 `(0.5,0.5)` 更省（改一行脚本、不动 shader）—— 值得先花 10 秒试一次。

### ❌ 实测：`position += (0.5,0.5)` 让画面"更奇怪" —— 必须撤回；并逐项排除偏移来源

**Ray 实测**：`_vision_mask.position = -MASK_SIZE * 0.5 + Vector2(0.5, 0.5)` ⇒ **没修正、反而更奇怪**。
**原因**：在**节点位置**上做半像素平移 ＝ 整个 **2048×2048** 的遮罩整体偏半像素 ⇒ **采样点全部落在纹素中间** ⇒ **整片被重采样**（Nearest 下表现为抖动/不均匀）✗
**⇒ 撤回该行**，并**不要再用"平移节点"的方式补偿半像素**（半像素平移必然重采样）。

**逐项实测排除（都是像素级扫描，非目测）**：

| 项 | 实测值 | 结论 |
|---|---|---|
| `full_radius` | **63.5** | ✓ `2r = 127` ＝ 帧图边长，**缩放匹配、无相位漂移** |
| 帧图圆心 vs 图中心 | `filter_0..4` 包围盒中心 (63,63)/(62,62)、质心 ≈ (63.1, 63.0)，图中心 (63,63) | ✓ **圆心基本就在图中心**（偏差 ≤0.15px，属像素圆正常不对称） |
| **玩家精灵（眼睛）在帧内是否居中** | `player.png` 32×64；每帧只有 **8 个不透明像素**（左右眼各 4），包围盒 `[6,6]..[9,9]` 等 ⇒ **盒中心 (7.5, 7)、质心 (7.25/7.75, …)** | ⚠️ **垂直方向比帧中心 (7.5,7.5) 高约 0.5px**；左右眼质心天然不对称 |

**⇒ 遮罩侧在数学上是对齐的**：`local = ±0.5` ↔ 纹素 63/64 ↔ canvas 像素 (79,78)/(80,79)，**1 纹素 = 1 像素，无相位错误**。
**⇒ 他看到的"偏"更可能来自：** ① 玩家精灵（眼睛）本身在 16×16 帧里不是几何居中（bbox 中心 y=7 vs 帧中心 7.5）；② 用大圆（`filter_4` 直径 117px）判断"居中"极易看错。

**建议诊断（20 秒）**：编辑器里选中 `MatchLight/VisionMask` → Material 设 **`Mask Tex = filter_0.png`（亮区只有 27px 直径）、`Radius = 63.5`** ⇒ **小圆的中心纹素（第 63 个）就是遮罩中心的准确指示**，一眼能看出偏没偏、往哪偏。
**若确认是精灵不居中** ⇒ **修 `player.png`**（把眼睛在 16×16 里摆正），而不是动遮罩。

### ✅ 根因确认（Ray 的关键观察）：**遮罩的采样点正好落在纹素边界上**

**Ray 的观察**：「感觉像是整个遮罩偏差了 0.5, 0.5，**遮罩的每个像素中心刚好就在游戏内四个像素的交点上**。」—— **完全正确**。

**数学验证**：shader 里 `uv = local/(2r) + 0.5`，`2r = 127` ⇒ `uv * 127 = local + 63.5`。
- game pixel 的**中心**相对遮罩中心的 `local = k + 0.5`（k 为整数）
- ⇒ `uv * 127 = k + 64.0` —— **正好是整数 ＝ 纹素边界** ✗（Nearest 会取到相邻两纹素之一，随浮点误差摆动 ⇒ 抖动/不均匀）
- 等价说法：遮罩中心落在 **canvas 整数点（像素交点）** 上 ⇒ 纹素中心也落在像素交点上。

**✅ 修法：在 `vision_mask.gdshader` 里给 `local` 减去 `(0.5, 0.5)`**（改那一行算式，不动节点位置）。
- 修后：`uv * 127 = k + 63.5` ⇒ **正好落在纹素中心** ✓
- 同时纹素边界与像素边界对齐 ⇒ **1 纹素 = 1 像素** ✓
- **方向上**：`local` 减小 ⇒ 采到图中更左上的纹素 ⇒ **图像内容往右下移 0.5** ✓ **正是 Ray 要的方向**

**⚠️ 为什么不能改节点 `position`**：`snap_2d_transforms_to_pixel = true` 会把 0.5 **吸附成整数（0 或 1）**，拿不到 0.5 ⇒ 这就是 `position += (0.5,0.5)` "更奇怪"的原因 ✓ **所以必须在 shader 里做。**

**方向对照（改 `local` 的符号）**：加 → 内容往**左上**移；**减 → 内容往右下移**（本次采用）。

### 🧩 最后一项需求：「玩家永远可见 + 只被墙遮挡 + 黑暗盖住墙」在数学上不可兼得 → 用「恒等渲染半径」化解

**Ray 的需求**：点灯前玩家精灵图也被黑色盖住；他希望**玩家不论是否点灯都正常显示，且仅被墙体瓦片遮挡**。

**三条需求互相矛盾**（单层 z 序 + 全屏遮罩下无解）：
1. `Cover` ＞ `Player`（墙遮挡玩家）
2. `VisionMask` ＞ `Cover`（黑暗盖住墙）
3. `Player` ＞ `VisionMask`（玩家永远可见）
⇒ 由 1+2 得 `VisionMask ＞ Cover ＞ Player`，与 3 的 `Player ＞ VisionMask` **直接矛盾** ✗
**这不是参数没调好，是机制的固有限制**（先前是靠"放弃第 3 条"绕过的；现在要把第 3 条拿回来，就必须换思路）。

**✅ 解法：让「渲染半径」恒定，光圈大小完全由「帧」决定** ⇒ 未点火时＝第 0 帧那张 **27px 小圆**，于是**玩家周围始终留一小圈可见**，同时黑暗区仍然看不见墙。

**改动只有一处**（`_set_radius()`）：
| 变量 | 取值 | 用途 |
|------|------|------|
| `_current_radius` | **`maxf(r, 0.0)`**（不动） | **判定**：0 ＝ 未照亮 ⇒ `is_position_illuminated()` 仍返回 false ✓ |
| **shader 的 `radius`** | **`maxf(r, full_radius)`**（下限 ＝ `full_radius` = 63.5） | **渲染**：始终 63.5 ⇒ 不缩放，**光圈大小只由帧决定** |

**效果链**：
- **未点火**：`radius = 63.5` + 第 0 帧（亮区直径 27px）⇒ **玩家周围一小圈可见，且看不到墙** ✓
- **点火**：帧 0 → 4 逐帧张开（27px → 117px）✓
- **全程**：玩家可见 ✓；`Cover` 仍在遮罩之下 ⇒ 黑暗区看不到墙 ✓；墙仍遮挡玩家 ✓
- **拾取判定**：`_current_radius` 仍是 0/63.5 ⇒ 行为不变 ✓

**若嫌 27px 太小**：把 `filter_0.png` 的圆画大一点（如 33px），或调 `full_radius` —— 但**别用 `filter_1`（53px）当待机帧**，那会缩短张开过程。

**备选（工作量大、冻线前不做）**：给 `Cover` 的 TileMapLayer 挂 shader，采样同一张序列帧、在光圈外自透明 ⇒ 三个需求可全满足，但要处理世界坐标映射（约 1~2 小时、易踩坑）。

**⚠️ 常见误解澄清**：**`maxf(r, full_radius)` 属于 GDScript，不能写进 shader**。
- `vision_mask.gdshader` 里的 `uniform float radius : hint_range(0.0, 2048.0) = 0.0;` **只是声明 + 默认值**，**保持原样不动**；`r` 与 `full_radius` 是脚本侧变量，**shader 根本看不到它们**（那样写会编译报错）。
- **要改的是脚本 `_set_radius()` 里"传给 shader 的值"那一处**：`_current_radius` 仍用于判定（保持 `maxf(r, 0.0)`），而 `set_shader_parameter("radius", …)` 的第二个参数换成 **`maxf(r, full_radius)`**。
- **一句话**：`uniform` 是**入口**（被动接收），不是**计算处**。
